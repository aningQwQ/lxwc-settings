# lxwc-settings 开发守则

本守则适用于 `lxwc-settings` 的所有代码、测试、文档和发布流程。

核心原则：

> **页面管意图，后端管解释，机制共享，策略独立。**

两条判据贯穿全文：

1. **机制共享，策略独立。** 写入、进程、事务、聚合这些错了会静默损坏用户配置的东西，只能有一份实现；选项语义、默认值、校验、页面交互、文案这些差异真实存在的东西，各模块自己实现。
2. **第三处再抽象。** 同一段逻辑出现第二份时，先复制并写清差异；出现第三份、且能指出三者共同的不变量时，才允许上移到 `config/`、`services/` 或 `pages/`。

## 1. 分层与依赖方向

```text
core        领域模型与能力接口：Effect、Task、ApplyReport、outputs::Outputs
config      配置契约：ConfigFile、ConfigFormat、ConfigEdit、PatchOutcome、CommandSpec
services    通用机制：文件事务、进程、后台 worker
plugin      插件清单：Plugin、provides/requires、capability 名称
plugins     所有可选单元与注册表
  mod.rs    探测、需求解析、组装 backend + pages + groups
  labwc/    后端插件：适配器、ConfigFormat、页面
  wlr/      输出提供者插件（无 UI）
  wlr_ui/   输出页面插件（requires outputs）
pages       预留的合成器无关页面（当前为空）
modules     页面契约：SettingsModule、ModuleMeta、ModuleCtx、StatusMessage
app         外壳：读取后端文件清单、按文件聚合任务、跨页面请求、确认与应用状态
ui          纯控件和样式
```

必须遵守：

- `core` 与 `config` 不得依赖 `plugins`、`pages`、`modules` 或 `ui`。
- `plugins/<id>/` 不得 import 另一个 `crate::plugins::<other>`；跨插件协作只能通过内核接口（如 `core::outputs::Outputs`）。
- 提供者插件（如 `plugins/wlr`）必须无 UI：不得 import `ui`、`modules`、`pages`。
- 页面插件与后端插件可以依赖内核契约（`modules`、`ui`、`backend`、`config`、`core`）。
- 后端适配器（`plugins/<backend>/*.rs` 顶层文件）不得依赖 `modules` 或 `ui`；页面放在其 `pages/` 子目录。
- `plugins/mod.rs` 是唯一注册表，只有它可以引用所有插件；`app` 只调用 `plugins::compose`。
- `pages/` 不得 import `crate::plugins`，也不得出现任何插件键空间（如 `/labwc_config`）。
- 主线（`app`、`modules`、`config`、`core`、`ui`、`plugin`）不得 import 任何具体插件。
- 插件不得自己持久化。插件页与普通页一样，只能产出 `ConfigEdit`/`Task`，由 `app` 聚合写入。
- 页面只能通过 `ConfigEdit.file_id` 和 `patch(file_id, raw)` 表达写入，不得出现路径、不得自己写文件。
- 持久化统一通过 `Effect::WriteFile` 和 `Effect::RunCommand`。
- 上述方向由 `src/architecture_tests.rs` 在测试期强制。

**插件可删除性**是这套约束的验收标准：

> 删除 `plugins/<id>/` 目录、注册表里的一行、对应 feature 与私有翻译键后，
> 项目必须能编译并通过测试，且内核不需要改动。

## 2. 公共契约（窄腰）

以下类型是“一个 app + N 个后端”的前提，必须共享，且**不得随意扩张**：

- `core::model`：`Effect`、`Task`、`TaskResult`、`ApplyReport`。
- `config`：`ConfigFile`、`ConfigEdit`、`ConfigFormat`、`PatchOutcome`、`CommandSpec`。
- `modules::SettingsModule` 及其 `ModuleMeta`、`ModuleCtx`、`StatusMessage`、`ModulePayload`。
- `plugin::Plugin` 与 `capability` 名称：插件清单的唯一形状。
- `core::outputs`：`Mode`、`OutputInfo`、`trait Outputs`。
- `Backend`、`Group`、`Deps`。

准入条件，缺一不可：

1. 至少有两个真实使用处。
2. 出错时是静默的或破坏性的（例如快照校验、原子替换）。
3. `app` 为了聚合、排序、去重或归属必须依赖它。
4. 接口能压到最小，并且能用测试表达它的不变量。

不满足条件的，一律留在使用处。**新增窄腰类型需要单独说明理由**，不接受“以后可能会用到”。

明确不允许上移的（属于策略）：

- baseline / desired 状态容器与 diff 方式。
- 表单字段、校验规则、输入约束。
- 刷新时机、缓存失效策略。
- 主题、字体、布局、输出的扫描与排序。
- 选项名、默认值、键空间、分组与页面顺序。
- 提示文案与错误措辞。

## 3. 文件与写入规则

- 文件路径、格式、解析、补丁、标记块、重载命令，归对应后端。
- 物理读取、备份、原子替换、快照校验，归 `services::fs`。
- 页面不得出现 `std::fs`、`services::fs`、`read_to_string` 等直接文件访问。
- 页面需要文件内容时，调用后端或页面状态模块的读取入口。
- 页面需要写入时，产出 `ConfigEdit` 或 `PatchOutcome`，由 `app` 汇总。

写入必须带期望快照：

```rust
Effect::WriteFile {
    path,
    contents,
    expected,
}
```

`expected` 用于检测外部修改，任何路径都不得绕过。

**同一文件的所有页面改动必须合并成一次写入。** 这是 `app` 聚合存在的理由：
页面各自写文件会产生多次写、多次快照校验和“后写覆盖先写”的竞态。

## 4. 命令规则

- `Command::new` 只能出现在 `services::process`。
- 子进程执行统一走 `services::process::run`。
- 命令参数拼装归对应位置：
  - `wlr-randr` 命令归 `plugins/wlr`（提供者）。
  - 重载命令归 `plugins/<id>/reconfigure.rs`，通过 `Backend.reload` 交给 `app`。
- 页面不得手写 `wlr-randr --output ...` 这类命令字符串。
- 实时显示切换属于 `wlr` 的异步 worker，不走 `Effect::WriteFile`。
- 持久化相关命令走 `Effect::RunCommand` 或 `services::process`。
- 一次应用最多触发一次重载；只有 `needs_reload` 的文件发生变化时才附带重载效果。

## 5. 页面与状态规则

页面只允许拥有：

- 页面控件与布局。
- 用户选择状态、编辑草稿、待执行变更。
- 错误与状态提示。
- `is_valid()` 之类的输入校验。
- 自己的刷新与缓存策略。

页面不允许：

- 直接读写文件或启动进程。
- 直接解析后端配置格式。
- 直接拼外部命令。
- 直接调用其他页面的实现。
- 在 `pages/` 中写死后端路径、键空间或重载命令。

**状态机由页面独立实现，不提供公共状态框架。** 但每个带编辑状态的页面，其测试必须覆盖同一组行为（用测试共享契约，而不是用代码共享实现）：

1. 成功回执后：没有待提交变更，界面回到已保存状态。
2. 失败回执后：草稿保留，且能从 `failures` 取到对应错误。
3. `refresh()` 后：baseline 与 desired 一致，没有待提交变更。
4. 未改动时：不产生 `ConfigEdit`，也不产生 `Task`。
5. 跨页面：多个页面修改同一文件时，`app` 只产生一个写任务（在 `app` 测试中覆盖）。

页面复用规则：

- `pages/` 是**可选实现库**，不是强制层。后端可以选择复用，也可以自己写一个。
- 两个页面“看起来一样”但选项名、措辞或校验不同时，保留两份，不要合并。
- 只有行为对用户完全一致时，才把页面移入或复制到 `pages/`。

## 6. 新增后端插件

1. 建 `src/plugins/<id>/`：`paths.rs`、`reconfigure.rs`、`formats.rs`、`pages/`。
2. 在 `formats.rs` 实现 `ConfigFormat`；格式实现由该插件拥有，不放进 `config/`。
3. 写 `backend()` 返回 `files`、`groups`、`reload`；写 `pages(ctx, deps)` 返回页面列表。
4. 导出 `pub const PLUGIN`：`provides` 包含 `capability::BACKEND`，`requires` 列出实际用到的能力，`backend`/`pages` 填工厂。
5. 在 `plugins/mod.rs` 的 `PLUGINS` 加一行（带 `#[cfg(feature = "...")]`），并在 `Cargo.toml` 增加对应 feature 与依赖边。
6. 需要探测时使用该后端的会话信号（如 `HYPRLAND_INSTANCE_SIGNATURE`、`SWAYSOCK`、`NIRI_SOCKET`、`WAYFIRE_SOCKET`），并保留 `LXWC_BACKEND` 强制覆盖。
7. 不得改动 `app`、`modules`、`ui`。若确实需要改动，说明当前内核契约缺了什么，而不是加分支。

文件描述统一为：

```rust
ConfigFile {
    id: "rc-xml",
    path: paths::rc_xml(),
    format: &formats::RC_XML,
    title_key: "rc_xml_changes",
    needs_reload: true,
}
```

## 7. 插件模型

角色不再由目录区分，而由 `Plugin` 清单表达：

- `provides`：本插件实现的能力（如 `backend`、`outputs`）。
- `requires`：本插件依赖的能力；组合根按 `requires ⊆ provides` 启用。
- `backend`：提供后端描述（文件、分组、重载）。
- `pages`：贡献页面；接收 `Deps`（如 `Arc<dyn Outputs>`），不 import 其他插件。
- `groups`：请求侧栏分组；宿主按 id 合并，后端已声明的顺序优先。
- `outputs`：提供某个能力的工厂（当前只有 `outputs`）。

规则：

- 内核包含：`core`、`config`、`modules`、`services`、`ui`、`plugin`、`app`。
- 一切可选内容都在 `plugins/`：后端、提供者、页面插件、预设。
- 能力接口放内核（`core::outputs::Outputs`）；提供者实现它，页面消费它，插件之间零 import。
- 组合根（`plugins/mod.rs`）解析需求；缺提供者时该插件不启用，不尝试运行半套。
- feature 图必须表达真实依赖：`wlr-ui = ["wlr"]`、`labwc = ["wlr", "wlr-ui"]`；`default` 是 `labwc`。
- `cargo build --offline --no-default-features` 必须通过，得到一个只显示“没有启用任何后端或插件”的外壳。
- 插件缺席时，`app` 不得 panic，也不得假装功能存在。
- `pages/` 只放合成器无关、且不依赖任何具体能力实现的页面。当前为空是正常状态。

## 8. 专有逻辑归属

- XML 解析、XPath、keybind、action 语法：`plugins/labwc/rc_xml.rs`
- environment 文件格式：`plugins/labwc/environment.rs`
- rc.xml / environment 的 `ConfigFormat`：`plugins/labwc/formats.rs`
- autostart 标记块：`plugins/labwc/autostart.rs`
- XKB 布局解析与合并：`plugins/labwc/layouts.rs`
- 快捷键组合键编辑语法：`plugins/labwc/keycombo.rs`
- 指针加速曲线语法：`plugins/labwc/accel.rs`
- openbox action 词汇：`plugins/labwc/actions.rs`
- 主题目录扫描：`plugins/labwc/themes.rs`
- WLR 输出解析、模式命令：`plugins/wlr/`

判断标准：

> 如果一段逻辑只对某个外部系统有意义，它就不能留在 `pages/` 或 `modules/`。

## 9. UI 约定

- 页面过长必须使用 `ScrollArea`。
- 不添加无意义外框，优先使用 `ui.scope`、`ui.separator` 和分节标题。
- 状态使用明确的成功、警告、错误颜色。
- 清除、禁用、空状态必须有明确反馈。
- 无效输入必须通过 `is_valid()` 阻止 Apply，而不是只显示提示。
- 高风险改动（可能让会话不可用）应提供确认或回退路径，并在页面内实现。

## 10. 国际化规则

- 用户可见文本只能通过 `t("key")` 或 `trf!("key", args)`。
- 不能在代码中硬编码中文或英文界面文本。
- 新键必须同时加入：
  - `locales/en-US.lang`
  - `locales/zh-CN.lang`
- 删除功能时同步删除无用翻译键。
- 新增的后端私有键使用可识别的前缀（例如 `labwc_`），共享文案保持无前缀；存量键在专门迁移时统一，不做零散改名。
- 当前是扁平键表，`t()` 没有编译期校验；改名时必须全局搜索并人工确认。
- README 以英文为主，中文内容放在 `README.zh-CN.md`。

## 11. Rust 与代码风格

- 使用 Rust 2021 和 egui/eframe 0.28。
- 默认不写注释，除非确实需要解释非显而易见的约束。
- 错误信息尽量使用翻译键。
- 优先返回 typed state，避免让页面反复拼字符串。
- 不引入未使用的抽象层；不为单一实现预留泛型或 trait。
- 新增逻辑优先放入已有后端、页面库、services 或 integrations，不随意新增顶层模块。
- 新增依赖前先确认现有依赖足够，避免为一次性需求引入 crate。

## 12. 测试规则

必须覆盖：

- 适配器：解析、补丁、标记块、命令拼装、格式幂等性。
- `services`：原子写入、备份、外部修改检测。
- 页面：第 5 节列出的五条一致性行为。
- 跨页面：多个页面修改同一文件时只生成一个写入任务。
- 架构：`src/architecture_tests.rs` 的依赖方向检查必须保持通过。

页面一致性测试是**改动页面时的要求**：新增页面必须一次写全，存量页面在下一次修改该页面时补齐，不做与功能无关的批量返工。

新增 `ConfigFormat` 时，至少提供：

- 从空文件/无该键的文件开始应用。
- 重复应用同一批编辑结果不变（幂等）。
- 保留未知键、注释和无关注释块。
- 删除键时只影响目标键。

提交前执行：

```bash
cargo fmt --check
cargo build --offline
cargo test --offline
cargo build --offline --no-default-features
cargo test --offline --no-default-features
cargo build --release --offline
```

真实配置校验：

```bash
LXWC_TEST_RC="$HOME/.config/labwc/rc.xml" cargo test real_config
```

## 13. 允许的例外

以下情况目前允许，但要谨慎：

- `plugins/labwc/themes.rs`、`plugins/labwc/layouts.rs` 直接扫描系统目录或读取 `evdev.lst`，因为路径和格式属于后端知识。
- `main.rs` 启动时读取字体文件，属于应用启动逻辑，不在页面层。
- `plugins/<id>/pages/` 中可以出现 XPath 字符串和环境变量键名，因为它们描述“改哪个配置项”；文件格式处理仍归适配器。
- `plugins/wlr_ui` 中的输出看门狗是插件私有实现。另一种输出机制若需要不同的回退语义（例如文件快照回退而不是命令回退），应各自实现；第三处出现时才考虑上移。
- `plugins/labwc/pages/display_persist` 可以维护当前选择、持久化模式和 autostart 快照，但不得重新实现 autostart 格式。

## 14. 提交前检查清单

- [ ] 页面没有直接访问文件或启动进程。
- [ ] 页面没有出现路径、后端键空间或重载命令。
- [ ] 插件之间没有互相 import，跨插件只走内核接口。
- [ ] 后端适配器没有依赖 `modules` 或 `ui`。
- [ ] `pages/` 没有 import `crate::plugins`。
- [ ] 没有为单一实现新增公共抽象。
- [ ] 新增文本已加入中英文翻译。
- [ ] 新增解析、补丁或状态逻辑有测试，页面有一致性测试。
- [ ] 页面可滚动，空状态和错误状态清晰。
- [ ] `cargo fmt --check` 通过。
- [ ] `cargo test --offline` 通过。
- [ ] `cargo build --offline --no-default-features` 通过（零插件外壳）。
- [ ] `cargo build --release --offline` 通过。

## 15. Git 与发布规则

- 未经明确要求不要 commit。
- 提交信息使用现有风格：
  - `feat:`
  - `fix:`
  - `refactor:`
  - `docs:`
  - `release:`
- 发布流程：
  - 更新 `Cargo.toml` 和 `Cargo.lock`
  - 构建 x86_64 release
  - 打包 `lxwc-settings-X.Y.Z-x86_64-linux.tar.gz`
  - 包内包含二进制、`LICENSE`、`README.md`、`README.zh-CN.md`
  - 打 tag `vX.Y.Z`
  - 推送并创建 GitHub Release
